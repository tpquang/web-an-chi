## Quy ước

- Kế hoạch mới đặt tên `YYYY-MM-ten-ke-hoach.md`. Tên file viết thường, không dấu, nối bằng gạch ngang.
- Sửa code làm thay đổi hiện trạng thì cập nhật docs trong cùng commit.
- Việc của backend ghi vào backlog của app cần nó.

## Backend

Không có thư mục riêng, nguồn chuẩn là code.

- **Stack:** Node.js, Express 5, Prisma 7, PostgreSQL. Chỉ `apps/api` truy cập database. Web gọi API từ server của Next, trình duyệt chỉ gọi route handler `/api/*` của web. Web cache dữ liệu 60 giây.
- **Vì sao PostgreSQL:** đơn hàng và tồn kho cần transaction, ràng buộc khoá ngoại; `JSONB` đủ cho thông số riêng từng loại trầm. Prisma giữ ở 7.x tới khi bản 8 ra chính thức.
- **Schema:** `apps/api/prisma/schema.prisma` gồm danh mục, sản phẩm, ảnh, chủ đề bài viết, bài viết, khách hàng, đơn hàng, cấu hình `Setting`. Tiền lưu số nguyên VND. Mọi thay đổi đi qua `npm run db:migrate`.
- **Dữ liệu ban đầu:** `apps/api/prisma/sample-data.json` (danh mục, nguyên liệu, công thức, hạt, bài viết), nạp bằng `npm run db:seed`. `scripts/deploy.sh` tự nạp lần cài đầu qua `db:seed:initial`, bỏ qua nếu database đã có hàng. `db:seed:reset` xoá sạch hàng hoá, đơn, kho, khách rồi nạp lại.
- **API công khai** (`/api/v1`): `categories`, `products` (lọc `category`, `featured`, phân trang), `post-categories`, `posts`, `settings/store`, `cart/quote`, `orders` (tạo đơn), `orders/:code` (không có thông tin cá nhân), `orders/lookup` (mã đơn + số điện thoại). `GET /health` kiểm cả database.
- **Tài khoản khách** (`/api/v1/account`): đăng ký, đăng nhập bằng số điện thoại và mật khẩu (scrypt), token 30 ngày, tối đa 8 lần sai mỗi số trong 15 phút. Số đã từng đặt hàng phải nhập mã một đơn cũ mới tạo được tài khoản. Đặt hàng khi đã đăng nhập thì đơn gắn vào tài khoản. Web giữ token trong cookie httpOnly. API không bao giờ trả `passwordHash`. Token mang `Customer.sessionVersion`, API so với database mỗi request; đổi mật khẩu (`POST /account/password`, phải nhập mật khẩu cũ nếu đã có) hoặc nhân viên đặt lại (`POST /admin/customers/:id/password`) thì tăng số này, mọi phiên cũ hết hiệu lực, phiên đang đổi nhận token mới. Chưa có quên mật khẩu tự phục vụ: khách nhắn shop. Đăng nhập Google (`GET/POST /account/google`, web điều hướng ở `apps/web/src/app/api/account/google/*`): OAuth code + PKCE, API đổi code lấy `id_token` (`lib/google.ts`), liên kết bằng `Customer.googleSub`. Khách tạo qua Google có `phone = null` tới khi tự bổ sung ở trang tài khoản hoặc đặt đơn đầu tiên (chỉ khi số chưa thuộc hồ sơ khác). Thiếu `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` thì tính năng tắt, cấu hình xem `docs/setup.md`.
- **Kho và đợt nhập** (`/api/v1/admin`: `materials`, `batches`, `recipes`, `pack`, `movements`): nhập nguyên liệu thô (nụ theo viên, hộp, thiệp...), đóng gói theo cấu thành của từng sản phẩm thành hàng bán (`Product.stock`). Hao hụt khi nhận hàng không vào kho, tiền của nó dồn vào giá vốn phần còn lại; chi phí phát sinh chia theo tỉ lệ tiền hàng (`apps/api/src/lib/inventory.ts`, CMS có bản sao để xem trước ở `apps/cms/src/lib/batch.ts`). Nhập kho cập nhật giá vốn bình quân, chỉ làm một lần, sau đó đợt bị khoá. Mọi thay đổi tồn kho ghi `StockMovement`. Lợi nhuận không gồm chi phí vận hành ban đầu. Điểm hoà vốn: theo đợt nhập, CMS xem trước số thành phẩm cần bán để thu đủ vốn đợt theo cơ cấu kế hoạch (`batchBreakEven` trong `apps/cms/src/lib/batch.ts`); theo tháng, báo cáo lợi nhuận trả `breakEven` (doanh thu hoà vốn = chi phí cố định / tỉ lệ lãi góp, `apps/api/src/lib/break-even.ts`), chỉ khi không lọc theo dòng sản phẩm hoặc kênh.
- **File 3D sản phẩm** (`ProductModel`, quản trị `PUT/GET/DELETE /admin/products/:id/model`, công khai `GET /products/:slug/model`): CMS tải `.glb` ở form sản phẩm (modal dùng chung với charm, `apps/cms/src/components/ModelUploadModal.tsx`), API kiểm byte đầu và giới hạn 15 MB (`lib/model-file.ts`). Web phục vụ qua `/api/models/<slug>?v=<mốc cập nhật>` cache lâu dài, trang sản phẩm có nút "Xem 3D" dựng bằng `components/box3d/glb.ts` trong khung xem chung. Sản phẩm có cả mẫu dựng sẵn (`model3d`) lẫn file thì hiện cả hai nút.
- **Trang nội dung tự soạn** (`/api/v1/pages`, quản trị ở `/api/v1/admin/pages`, model `Page`): bảo hành, chính sách đại lý, cộng tác viên... Web hiện ở `/<slug>` (`apps/web/src/app/(store)/[slug]`), trang bật "Hiện ở cuối trang" có link trong footer, trang không `noindex` có trong sitemap. Slug không được trùng route tĩnh của web (`RESERVED_PAGE_SLUGS` trong `admin.pages.ts`); đổi slug thì ghi redirect 308 như bài viết. Nút cuối trang có thể là `#chat` để mở khung chat. Seed tạo sẵn 3 trang ở trạng thái nháp, chỉ tạo khi chưa có.
- **Chat với khách** (`/api/v1/chat` cho web, `/api/v1/admin/inbox` cho CMS): khách nhắn từ khung chat trên web, nhân viên trả lời trong Hộp thư CMS. Tin mới đẩy tức thì bằng Server-Sent Events qua một kênh phát trong bộ nhớ (`lib/chat-bus.ts`); chạy nhiều tiến trình API thì phải đổi sang Redis hoặc Postgres LISTEN/NOTIFY. Trình duyệt khách nhận diện bằng mã ngẫu nhiên trong cookie httpOnly của web, API chỉ lưu bản băm. Hội thoại tự gắn với khách theo tài khoản đang đăng nhập hoặc số điện thoại. Trường `channel` để sẵn cho Facebook, Zalo.
- **Nhân viên** (`/api/v1/admin/staff`): mỗi người một tài khoản, quyền Chủ shop hoặc Bán hàng. Bán hàng không vào được vốn, kho, nhân viên. Tài khoản trong `.env` tự thành Chủ shop ở lần đăng nhập đầu.
- **API quản trị** (`/api/v1/admin`): đăng nhập bằng tài khoản nhân viên (`StaffUser`, mật khẩu scrypt) hoặc tài khoản chủ shop trong biến môi trường; token HMAC 12 giờ, tối đa 10 lần sai mỗi IP trong 15 phút. Quyền theo ma trận ở `lib/permissions.ts`. CRUD danh mục, sản phẩm, chủ đề, bài viết, trang nội dung; xem khách hàng; xử lý đơn (`admin.orders.ts`); số liệu tổng quan.
- **IP của khách:** API chỉ tin `X-Real-IP` khi kết nối đến từ chính máy chủ (nginx hoặc route handler web, `lib/client-ip.ts`); route handler web chuyển IP khách sang API (`forward` có `clientIp`). Production API chỉ nghe `127.0.0.1`.
- **Đặt hàng:**
  - Giá và phí giao tính ở server. Trừ tồn kho có điều kiện trong transaction nên hai đơn cùng lúc không bán quá số còn.
  - Khoá `idempotencyKey` chống tạo đơn trùng. Khách được tạo hoặc cập nhật theo số điện thoại.
  - Web gửi `expectedTotalVnd`; giá đổi trong lúc khách điền form thì API trả 409 `PRICE_CHANGED`.
  - Tối đa 5 đơn mỗi IP trong 10 phút, 3 đơn đang chờ chuyển khoản mỗi số điện thoại (429).
  - Đơn mới, khách huỷ, hệ thống huỷ báo CMS qua SSE `/admin/inbox/stream` (sự kiện `order`).
- **Vòng đời đơn** (`modules/orders/order-flow.ts`, kế hoạch ở `docs/web/plans/order-flow-2026-11.md`):
  - Luật chuyển: PREORDER → PENDING, CONFIRMED; PENDING → CONFIRMED; CONFIRMED → SHIPPING; SHIPPING → COMPLETED, RETURNED; COMPLETED → RETURNED; CANCELLED → PENDING (mở lại). Sai luật thì 409 `BAD_TRANSITION`.
  - Kho giữ ở mọi trạng thái trừ Đặt chờ, Huỷ, Hoàn hàng.
  - Huỷ qua `cancelOrder`, có lý do và người huỷ. Khách tự huỷ khi PREORDER, PENDING (`POST /orders/:code/cancel` kèm số điện thoại); shop huỷ được tới CONFIRMED; đang giao thì chỉ Hoàn hàng.
  - Tiền hoàn gợi ý: hoàn hết tiền đã nhận, trừ tiền cọc khi đơn có hàng làm riêng (vòng tự thiết kế, sản phẩm `requiresDeposit`) đã xác nhận. Hoàn hàng: trừ phí giao.
  - Tiền: `paidVnd` cộng dồn khi shop ghi nhận; `paymentStatus` suy ra. Giao xong đơn COD tự ghi đã thu đủ. Có tiền phải hoàn thì `refundVnd`, `refundedAt` khi đã hoàn.
  - Hạn chuyển khoản `paymentDueAt` (đơn chuyển khoản hoặc cần cọc, `store.paymentHoldHours`, mặc định 24 giờ). Việc nền `jobs.ts` mỗi 5 phút huỷ đơn quá hạn chưa nhận đủ, trả kho. Shop xác nhận đơn thì bỏ hạn.
  - Lịch sử `OrderEvent`: tạo đơn, đổi trạng thái, nhận tiền, hoàn tiền, ghi chú nội bộ; ai làm (nhân viên, Khách, Hệ thống).
  - Admin: `GET /orders?view=todo|payment|preorder|confirmed|shipping|refund`, `GET /orders/counts`, `POST /orders/:id/transition|cancel|payment|refund|notes`. `PATCH` chỉ sửa đối soát (phí sàn, ship thực trả, cọc, mã vận đơn, mã sàn).
- **Đặt chờ** (đi qua giỏ hàng như đơn thường): trước ngày mở bán, khách vẫn thêm vào giỏ và đặt hàng ở trang thanh toán (đủ tên, số điện thoại, địa chỉ). API tự biết đơn là đơn đặt chờ khi chưa tới giờ mở bán (`launchAt` trong setting `store`, sửa ở CMS > Thông tin cửa hàng), khách không tự chọn được. API: báo giá đặt chờ không chặn hết hàng hay thiếu hàng, tính đủ giá; đơn vào trạng thái `PREORDER` (CMS và web: "Chờ chuẩn bị"), có phí giao như thường, chưa trừ kho. Giỏ hàng và trang thanh toán hiện ghi chú "Đơn đặt chờ" (`components/cart/preorder-note.tsx`). Shop chuẩn bị hàng rồi chuyển trạng thái theo vòng đời đơn: vào trạng thái giữ kho thì trừ kho (thiếu hàng thì báo lỗi). Báo cáo lợi nhuận không tính đơn chờ chuẩn bị. Bật tắt ở CMS > Cài đặt cửa hàng (`preorderEnabled` trong setting `store`, chưa lưu thì coi như bật); tắt thì trước ngày mở bán web ẩn nút thêm vào giỏ, báo giá trả `preorderClosed` và API từ chối đơn (403 `PREORDER_OFF`). Đơn đặt chờ cũ chưa có địa chỉ vẫn dùng "Chuyển thành đơn chính" (`POST /admin/orders/:id/convert`) ở chi tiết đơn.
- **Thanh toán:** khi nhận hàng (COD) hoặc chuyển khoản (chỉ khi cửa hàng có tài khoản ngân hàng, API trả 400 `NO_BANK` nếu không). Chưa có cổng thanh toán online, shop ghi nhận tiền ở chi tiết đơn trên CMS.
- **Đặt cọc:** setting `store.deposit` `{ enabled, percent 30–50, forCustom, forPreorder, forMarked, minOrderVnd }` (dạng cũ có `scope` vẫn đọc được). Đơn cần cọc khi trúng một điều kiện: vòng tự thiết kế, đặt chờ, có sản phẩm `requiresDeposit`, tạm tính từ `minOrderVnd`. Báo giá trả `payment: { bankTransfer, deposit: { percent, amountVnd, reasons }, holdHours }`; đơn trả khi nhận hàng lưu `Order.depositVnd` = phần trăm của tạm tính, làm tròn lên nghìn đồng (`depositFor` ở `lib/store.ts`). Chuyển khoản cả đơn thì không cọc. `GET /orders/:code` trả thông tin chuyển khoản kèm `amountVnd` là số còn phải chuyển, hạn, mốc trạng thái, `canCancel`, `madeToOrder`. Trạng thái thanh toán có `DEPOSITED` ("Đã nhận cọc"); CMS sửa được `depositVnd` ở khối Đối soát khi đơn chưa xác nhận.
